## 🔹 LINUX + SHELL SCRIPTING

### 01) How would you troubleshoot high CPU usage on a production Linux server?

**Approach:**

1. **Identify the problem scope** — `top` or `htop` to see overall CPU usage and the top consuming processes.
2. **Drill into per-core usage** — `mpstat -P ALL 1` (from `sysstat`) to see if only specific cores are overloaded.
3. **Find the guilty process** — `top -c` shows the full command line. Note the PID.
4. **Inspect threads** — `top -H -p <PID>` to find which thread within the process is consuming CPU.
5. **Check system vs user CPU** — `vmstat 1` to determine if CPU is burned in user space (`us`) or kernel space (`sy`).
6. **Profile the process** — `strace -p <PID> -c` or `perf record -p <PID>` to see syscalls or hot functions.
7. **Review recent load** — `sar -u` from `sysstat` to see if this is a spike or sustained.
8. **Check for runaway processes** — look for processes in `R` (running) or `D` (uninterruptible sleep) state.

**Key Commands:** `top`, `htop`, `vmstat`, `mpstat`, `pidstat`, `sar`, `strace`, `perf`, `iostat`

### 02) How would you identify memory leaks and OOM kills?

**Memory Leaks:**

1. **Track memory over time** — `top` or `ps aux --sort=-%mem` to identify processes growing steadily.
2. **Examine process memory** — `cat /proc/<PID>/status | grep -i vm` and `cat /proc/<PID>/smaps` for detailed breakdown.
3. **Historical trend** — `sar -r` to check free/buff/cache memory over time.
4. **Per-process RSS** — `smem -t -s rss -r` for accurate memory accounting.
5. **Application-level** — check application logs for allocation warnings; use tools like `valgrind --leak-check=full` for development.

**OOM Kills:**

1. **Check kernel log** — `dmesg | grep -i oom` or `grep -i oom /var/log/kern.log`
2. **Check syslog** — `journalctl | grep -i "out of memory"` or `grep "Out of memory" /var/log/messages`
3. **Inspect OOM score** — `cat /proc/<PID>/oom_score` to see which processes are most likely to be killed.
4. **Review OOM adjustments** — `/proc/<PID>/oom_score_adj` and sysctl `vm.overcommit_memory`.
5. **Check available memory** — `free -h` and look at `-/+ buffers/cache` for real available memory.

**Key Commands:** `dmesg`, `grep oom`, `free -h`, `sar -r`, `smem`, `valgrind`, `journalctl`

### 03) How would you debug intermittent network connectivity from Linux?

**Approach:**

1. **Continuous ping** — `ping -i 0.2 <host>` to spot packet loss in real time.
2. **Traceroute** — `traceroute <host>` or `mtr <host>` (better for intermittent issues) to find where packets drop.
3. **Check DNS resolution** — `nslookup`, `dig <host>`, `host <host>` — compare with repeated `nslookup` to catch intermittent DNS failures.
4. **Interface errors** — `ip link show` and `ethtool <interface>` for errors, drops, carrier state.
5. **Network statistics** — `netstat -s` or `ss -s` for protocol-level drop/retransmit counts.
6. **ARP issues** — `arp -n` or `ip neigh` to detect ARP table problems.
7. **Firewall rules** — `iptables -L -n -v` or `nft list ruleset` for dropped/filtered packets.
8. **Capture traffic** — `tcpdump -i <iface> host <target>` or `wireshark` to inspect actual packets.
9. **Route table** — `ip route show` to verify correct routing.

**Key Commands:** `mtr`, `ping`, `traceroute`, `tcpdump`, `dig`, `ip link`, `ethtool`, `ss`, `iptables`

### 04) Write a Bash approach to monitor disk usage and alert on thresholds.

```bash
#!/bin/bash
# disk_monitor.sh - Monitor disk usage and alert when thresholds are exceeded

THRESHOLD_WARN=80
THRESHOLD_CRIT=90
LOG_FILE="/var/log/disk_monitor.log"
EMAIL="admin@example.com"

timestamp=$(date '+%Y-%m-%d %H:%M:%S')

df -h --output=target,pcent | tail -n +2 | while read -r mount usage; do
    usage_num=${usage%\%}

    if [ "$usage_num" -ge "$THRESHOLD_CRIT" ]; then
        msg="CRITICAL: Disk usage on ${mount} is ${usage}% at ${timestamp}"
        echo "$msg" >> "$LOG_FILE"
        echo "$msg" | mail -s "Disk CRITICAL: ${mount}" "$EMAIL"
    elif [ "$usage_num" -ge "$THRESHOLD_WARN" ]; then
        msg="WARNING: Disk usage on ${mount} is ${usage}% at ${timestamp}"
        echo "$msg" >> "$LOG_FILE"
        echo "$msg" | mail -s "Disk WARNING: ${mount}" "$EMAIL"
    fi
done
```

**Deployment:** Add to crontab to run every 5 minutes: `*/5 * * * * /path/to/disk_monitor.sh`

**Enhancements:**
- Use `inotifywait` or `snmp` for real-time monitoring
- Integrate with PagerDuty/Slack webhooks for instant alerts
- Track inodes with `df -i`

### 05) How would you safely manage processes, signals and graceful shutdowns?

**Signal Management:**

| Signal | Number | Purpose |
|--------|--------|---------|
| SIGTERM | 15 | Graceful shutdown (default `kill`) |
| SIGKILL | 9 | Forceful termination (cannot be caught) |
| SIGHUP | 1 | Reload config without restart |
| SIGINT | 2 | Interrupt (Ctrl+C) |
| SIGSTOP | 19 | Pause process (cannot be caught) |

**Graceful Shutdown Pattern:**

```bash
#!/bin/bash
# graceful_shutdown.sh
PID=$1
TIMEOUT=30

if [ -z "$PID" ]; then
    echo "Usage: $0 <PID>"
    exit 1
fi

# Send SIGTERM for graceful shutdown
kill -SIGTERM "$PID"

# Wait for process to exit
for i in $(seq 1 $TIMEOUT); do
    if ! kill -0 "$PID" 2>/dev/null; then
        echo "Process $PID stopped gracefully"
        exit 0
    fi
    sleep 1
done

# Force kill if still running
echo "Process $PID did not stop, sending SIGKILL"
kill -SIGKILL "$PID"
```

**Best Practices:**
- Always send `SIGTERM` first, wait, then `SIGKILL` as fallback
- Use `trap` in scripts to handle cleanup: `trap 'rm -f /tmp/lockfile; exit' SIGTERM SIGINT`
- Use `systemd` for service management with `TimeoutStopSec=` directive
- Check for child processes: `pgrep -P $PID` and terminate the process tree
- Use `killall`, `pkill`, or `systemctl stop` for named services

### 06) How would you troubleshoot DNS, ports and connection failures?

**DNS Troubleshooting:**

1. **Check resolution** — `nslookup <host>`, `dig <host> @<dns_server>`, `host <host>`
2. **Check `/etc/resolv.conf`** — verify nameserver entries
3. **Check `/etc/hosts`** — look for overriding static entries
4. **Test specific DNS server** — `dig @8.8.8.8 <host>` to rule out local DNS issues
5. **Check DNS cache** — `systemd-resolve --statistics` or `nscd` cache

**Port Troubleshooting:**

1. **Check listening ports** — `ss -tlnp` or `netstat -tlnp`
2. **Test connectivity** — `nc -zv <host> <port>`, `telnet <host> <port>`, or `curl -v telnet://<host>/<port>`
3. **Check firewall** — `iptables -L -n -v`, `ufw status`, or cloud security groups

**Connection Failures:**

1. **Connection refused** — no service listening on that port: `ss -tlnp | grep <port>`
2. **Connection timed out** — firewall or network issue: `tcpdump`, `traceroute`
3. **Reset by peer** — service rejected the connection: check application logs
4. **Use `curl -v`** for HTTP failures to see full handshake details
5. **SSL/TLS issues** — `openssl s_client -connect <host>:443 -servername <host>`

**Key Commands:** `dig`, `nslookup`, `ss`, `nc`, `curl -v`, `tcpdump`, `iptables`, `openssl s_client`

### 07) How would you automate log analysis using Bash and standard Unix tools?

**Common Log Analysis Patterns:**

```bash
# 1. Find top 10 error occurrences
grep -i "error" /var/log/app.log | awk '{print $NF}' | sort | uniq -c | sort -rn | head -10

# 2. Count HTTP 5xx errors in last hour
LATEST_HOUR=$(date '+%d/%b/%Y:%H')
grep "$LATEST_HOUR" /var/log/nginx/access.log | grep '" 5[0-9][0-9] ' | wc -l

# 3. Extract slow requests (>5 seconds)
awk '$NF > 5.0 {print}' /var/log/nginx/access.log

# 4. Real-time log monitoring
tail -f /var/log/app.log | grep --line-buffered -i "error\|exception\|fatal"

# 5. Parse JSON logs (with jq)
cat /var/log/app.json | jq 'select(.level == "ERROR") | .message'

# 6. Log rotation monitoring
find /var/log -name "*.log" -size +1G -exec ls -lh {} \;
```

**Automated Analysis Script:**

```bash
#!/bin/bash
# log_analyzer.sh - Automated daily log analysis report

LOG_DIR="/var/log/app"
REPORT="/tmp/log_report_$(date +%F).txt"

{
    echo "=== Daily Log Analysis Report ==="
    echo "Date: $(date)"
    echo ""

    echo "--- Error Summary ---"
    grep -c "ERROR" "$LOG_DIR/app.log" && echo "errors found"

    echo "--- Top 5 Error Types ---"
    grep "ERROR" "$LOG_DIR/app.log" | sed 's/.*ERROR //' | sort | uniq -c | sort -rn | head -5

    echo "--- Response Time Percentiles ---"
    awk '{print $NF}' "$LOG_DIR/access.log" | sort -n | awk '
        {a[NR]=$1}
        END {
            print "P50: " a[int(NR*0.5)]
            print "P95: " a[int(NR*0.95)]
            print "P99: " a[int(NR*0.99)]
        }'

    echo "--- Failed Requests (4xx/5xx) ---"
    awk '$9 >= 400 {print $9}' "$LOG_DIR/access.log" | sort | uniq -c | sort -rn
} > "$REPORT"

mail -s "Daily Log Report" admin@example.com < "$REPORT"
```

**Key Tools:** `grep`, `awk`, `sed`, `sort`, `uniq`, `cut`, `wc`, `tail`, `jq`, `logrotate`

## 🔹 DOCKER + CONTAINERS

### 08) How would you reduce Docker image size and build time?

**Reduce Image Size:**

1. **Use multi-stage builds** — compile in one stage, copy only artifacts to a minimal runtime image.
   ```dockerfile
   # Build stage
   FROM golang:1.22 AS builder
   WORKDIR /app
   COPY . .
   RUN go build -o myapp

   # Runtime stage
   FROM alpine:3.19
   COPY --from=builder /app/myapp /usr/local/bin/myapp
   CMD ["myapp"]
   ```
2. **Use slim/minimal base images** — `python:3.12-slim`, `node:20-alpine`, `distroless`
3. **Combine RUN instructions** — use `&&` to avoid unnecessary layers, clean up in the same layer:
   ```dockerfile
   RUN apt-get update && apt-get install -y --no-install-recommends <packages> \
       && rm -rf /var/lib/apt/lists/*
   ```
4. **Use `.dockerignore`** — exclude `node_modules`, `.git`, `*.md`, test files, build artifacts
5. **Use `COPY --chmod`** to avoid extra `RUN chmod` steps
6. **Remove unnecessary packages** — uninstall build tools in the final image

**Reduce Build Time:**

1. **Order Dockerfile instructions by change frequency** — put least-changing layers (base image, dependencies) first to leverage layer caching.
2. **Copy `package.json` before source** — so dependency install layer caches when only code changes.
3. **Enable BuildKit** — `DOCKER_BUILDKIT=1 docker build .` for parallel layer builds and better caching.
4. **Use `--target`** for multi-stage to build only needed stages in dev.
5. **Cache mount for dependencies** — `--mount=type=cache,target=/root/.cache/pip`

### 09) How would you troubleshoot a container that repeatedly restarts?

**Systematic approach:**

1. **Check container status** — `docker ps -a` to see restart count and `Restarting` status.
2. **View logs** — `docker logs --tail 100 -f <container>` to see the last error before crash.
3. **Inspect the container** — `docker inspect <container>` to see `State`, `RestartCount`, `ExitCode`, `OOMKilled`.
4. **Check if OOM killed** — `docker inspect <container> | grep OOMKilled` — if true, increase memory limits.
5. **Run manually** — `docker run -it --entrypoint /bin/sh <image>` to enter the container and debug interactively.
6. **Check health check failures** — look at `Health` section in `docker inspect` output.
7. **Verify environment variables** — `docker inspect <container> | grep -A 20 Env` — missing or wrong env vars cause startup crashes.
8. **Check volume mounts** — wrong paths or permissions cause startup failures.
9. **Review restart policy** — `docker inspect <container> | grep -A 5 RestartPolicy` — `always` vs `on-failure`.
10. **Application config** — invalid config files, missing database connections, or port conflicts.

**Common causes:**
- Application crashes on startup (bad config, missing env vars)
- OOM (memory limit too low)
- Health check misconfiguration
- Port already in use on host
- Permission issues on mounted volumes

### 10) Explain container networking and DNS troubleshooting.

**Container Networking Models:**

| Driver | Use Case |
|--------|----------|
| `bridge` | Default, containers on same host communicate via bridge |
| `host` | Container shares host's network namespace, no isolation |
| `none` | No networking, manually configure |
| `overlay` | Multi-host networking (Swarm, Kubernetes) |
| `macvlan` | Container gets its own MAC address on physical network |

**Key Concepts:**

- Docker creates a `docker0` bridge by default; containers get IPs from `172.17.0.0/16`
- DNS resolution uses the host's DNS or custom DNS servers configured via `--dns`
- Containers can reach each other by name in user-defined bridges but not the default bridge

**DNS Troubleshooting:**

1. **Check container DNS config** — `docker inspect <container> | grep -A 5 Dns`
2. **Test DNS from container** — `docker run --rm alpine nslookup <host>`
3. **Check `/etc/resolv.conf` inside container** — `docker exec <container> cat /etc/resolv.conf`
4. **Link-local DNS** — Docker's embedded DNS server at `127.0.0.11` (in containers)
5. **Custom networks** — `docker network inspect <network>` to see connected containers and DNS configs

**Common Issues:**
- Container cannot resolve external hosts → check host DNS and Docker DNS config
- Container cannot resolve sibling containers → use user-defined bridge networks
- DNS resolution slow → check upstream DNS server, consider caching with `dnsdock` or `coredns`

### 11) How would you securely manage secrets in containerized workloads?

**Approaches (increasing security):**

1. **Environment Variables (not recommended for production)** — passed via `docker run -e` or `docker-compose`. Visible in `docker inspect`, process listings.
2. **Docker Secrets (Swarm only)** — `docker secret create <name> <file>` — encrypted at rest, mounted as files in `/run/secrets/`.
3. **External Secret Managers:**
   - **HashiCorp Vault** — dynamic secrets, lease-based rotation, KV storage
   - **AWS Secrets Manager / SSM Parameter Store** — integrate via SDK or sidecar
   - **Azure Key Vault** — managed identity access
   - **GCP Secret Manager** — IAM-based access control
4. **Kubernetes Secrets** — `kubectl create secret`, mounted as volumes or env vars; encrypted at rest with EncryptionConfiguration.
5. **Sealed Secrets / External Secrets Operator** — encrypt secrets in Git, decrypt at runtime.

**Best Practices:**
- **Never** commit secrets to Git or bake into images
- Use `.dockerignore` and pre-commit hooks to prevent accidental commits
- Use **read-only filesystem** for containers (`read_only: true` in compose, `readOnlyRootFilesystem` in K8s)
- Mount secrets as **files** rather than environment variables (avoid leaking in process listings)
- Rotate secrets regularly; use dynamic secrets where possible
- Use **mTLS** between services
- Scan images and builds for hardcoded secrets with tools like **gitleaks**, **trufflehog**

### 12) How would you investigate container CPU and memory throttling?

**CPU Throttling:**

1. **Check cgroup stats** — `cat /sys/fs/cgroup/cpu/docker/<container-id>/cpu.stat`
   - `nr_throttled` > 0 means CPU throttling occurred
   - `throttled_time` shows total throttled nanoseconds
2. **Docker stats** — `docker stats --no-stream` for real-time CPU/memory usage
3. **Check limits** — `docker inspect <container> | grep -A 5 CpuPeriod` to see `CpuQuota` and `CpuPeriod`
4. **Inside container** — `top` or `htop` to see if process is CPU-bound
5. **Kernel stats** — `pidstat -t 1 <PID>` to see per-thread CPU and delay

**Memory Throttling/OOM:**

1. **Check memory usage** — `docker stats` to see usage vs limit
2. **OOM killed** — `docker inspect <container> | grep OOMKilled`
3. **cgroup memory stats** — `cat /sys/fs/cgroup/memory/docker/<id>/memory.stat`
4. **Check `oom_score`** — inside container, `cat /proc/self/oom_score`

**Resolution:**
- Increase CPU/memory limits if consistently throttled
- Optimize the application (reduce memory footprint, fix leaks)
- Use `docker update --cpus --memory` to adjust without restarting
- Scale horizontally instead of increasing limits

**Static Image Scanning:**

6. **Policy enforcement** — use **OPA/Conftest** or **Docker Content Trust** to block vulnerable images
7. **Pre-build scanning** — scan `package.json`, `requirements.txt`, `go.mod` before building
8. **Quarantine & block** — use **Notary**, **Harbor**, or **AWS ECR** image scanning to prevent deployment of vulnerable images

### 14) How would you troubleshoot a Pod stuck in CrashLoopBackOff?

**Systematic approach:**

1. **Describe the pod** — `kubectl describe pod <pod> -n <ns>` — check `Last State`, `Exit Code`, `Restart Count`, `Events`
2. **View logs** — `kubectl logs <pod> -n <ns> --tail=100` and `kubectl logs <pod> -n <ns> --previous` (logs from the previous crashed container)
3. **Run manually** — `kubectl run -it --image=<image> --rm --restart=Never debug-shell -- /bin/sh` to test the image interactively
4. **Common causes and fixes:**

| Cause | Fix |
|-------|-----|
| Application error on startup | Fix the bug, check logs |
| Missing/wrong environment variables | Verify ConfigMap/Secret references |
| Missing config file / volume mount | Check `volumeMounts` and `volumes` |
| Liveness probe failing immediately | Adjust `initialDelaySeconds` or probe endpoint |
| Insufficient resources (OOMKilled) | Increase `resources.limits.memory` |
| Wrong command/entrypoint | Fix `command`/`args` in deployment |
| Dependency not ready (database) | Add `initContainers` or startup probes |
| Permission denied on mounted files | Check `fsGroup`, `runAsUser`, `subPath` |

5. **Check events** — `kubectl get events -n <ns> --sort-by='.lastTimestamp'`
6. **Check resource quotas** — `kubectl describe quota -n <ns>` for namespace limits
7. **Verify image** — `kubectl get pod <pod> -o jsonpath='{.spec.containers[0].image}'`

### 15) How would you debug Pending Pods caused by scheduling constraints?

**Debug steps:**

1. **Describe the pod** — `kubectl describe pod <pod>` — check `Events` for scheduling failures.
2. **Common causes:**

| Reason | Diagnosis | Fix |
|--------|-----------|-----|
| Insufficient CPU/memory | `kubectl describe node` shows allocatable vs allocated | Scale up nodes or reduce requests |
| No matching node selectors | Pod has `nodeSelector` no node satisfies | Add labels to nodes or remove selector |
| Taints without tolerations | `kubectl describe node` shows taints | Add `tolerations` to pod spec |
| Resource quota exceeded | `kubectl describe quota -n <ns>` | Increase quota or reduce requests |
| Pod affinity/anti-affinity rules | Events show "no nodes available" | Relax affinity rules or add more nodes |
| PVC not bound | `kubectl get pvc` shows Pending | Check `storageClass`, provisioner |
| Insufficient ephemeral storage | Node disk pressure | Clean up or add nodes |
| Topology spread constraints | Events show topology errors | Adjust `topologyKey` or constraints |

3. **Check node conditions** — `kubectl get nodes` and `kubectl describe node <node>` for `Ready` status and conditions.
4. **Dry-run scheduling** — `kubectl get pods --field-selector=spec.nodeName= -o wide` and manually test:
   ```bash
   kubectl run test-pod --image=nginx --dry-run=server -o yaml | kubectl apply -f -
   ```
5. **Descheduler** — use `descheduler` to rebalance and check for better placement.

### 16) How would you troubleshoot Service-to-Pod connectivity?

**Systematic approach:**

1. **Verify the Service exists and has endpoints:**
   ```bash
   kubectl get svc <service> -n <ns>
   kubectl get endpoints <service> -n <ns>   # Must show pod IPs
   ```
2. **Check selector matching** — `kubectl get pods -l <selector>` must return the expected pods.
3. **Test from inside a pod:**
   ```bash
   kubectl run debug --image=nicolaka/netshoot -it --rm --restart=Never
   # Inside the pod:
   curl <service-name>:<port>
   nslookup <service-name>
   nc -zv <service-name> <port>
   ```
4. **Check ClusterIP and port mapping** — `kubectl describe svc <service>` — ensure `targetPort` matches the container port.
5. **Network Policies** — `kubectl get networkpolicies -n <ns>` — check for deny rules blocking traffic.
6. **CNI issues** — check CNI pod logs: `kubectl get pods -n kube-system` and logs of `calico`, `flannel`, `cilium`.
7. **DNS resolution** — `kubectl run debug --image=busybox --rm -it --restart=Never -- nslookup <service>.<namespace>.svc.cluster.local`
8. ** kube-proxy** — check `iptables` or `IPVS` rules: `kubectl get pods -n kube-system | grep kube-proxy` and its logs.

**Common Issues:**
- Endpoints empty → selector mismatch, pods not Ready
- DNS not resolving → CoreDNS issues
- Connection refused → app not listening on `targetPort`
- NetworkPolicy blocking → review ingress/egress rules

### 17) How would you diagnose failing readiness and liveness probes?

**Liveness Probe** — determines if the container should be restarted:

1. **Check probe config** — `kubectl describe pod <pod>` under `Liveness`
2. **Common failures:**
   - `initialDelaySeconds` too short → app not ready yet
   - Wrong path/port → app doesn't expose the probe endpoint
   - Probe too aggressive (`periodSeconds` too low, `failureThreshold` too low)
   - App is slow to respond → increase `timeoutSeconds`

**Readiness Probe** — determines if the pod should receive traffic:

1. **Check if pod is in Ready state** — `kubectl get pods` — `0/1` means not ready
2. **Impact** — endpoints removed from Service, no traffic routed
3. **Common failures:**
   - Dependency (database, cache) not yet available
   - App initialization takes longer than `initialDelaySeconds`
   - Probe endpoint itself has a bug

**Startup Probe** — prevents liveness from killing a slow-starting container:

1. **Add startup probe** — `startupProbe` with higher `failureThreshold` and `periodSeconds`
2. **Disables liveness/readiness until startup succeeds**

**Debugging commands:**
```bash
# Check probe results in events
kubectl describe pod <pod> | grep -A 20 "Events"

# Manually test the probe endpoint
kubectl exec <pod> -- curl -v http://localhost:<port>/<path>

# Check probe configuration
kubectl get pod <pod> -o jsonpath='{.spec.containers[0].livenessProbe}'
```

**Best Practices:**
- Use different endpoints for liveness vs readiness when possible
- Set generous `initialDelaySeconds` for slow-starting apps
- Use `startupProbe` for apps with variable startup times
- Keep probes lightweight and fast

### 18) How would you perform a zero-downtime rolling deployment?

**Kubernetes Rolling Update Strategy:**

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # Max extra pods during update
      maxUnavailable: 0    # Never take pods down (zero downtime)
```

**Key Requirements:**

1. **Readiness probes** — must be configured; new pods only receive traffic when ready.
2. **Graceful shutdown** — handle `SIGTERM`, finish in-flight requests, close connections:
   ```yaml
   terminationGracePeriodSeconds: 30
   lifecycle:
     preStop:
       exec:
         command: ["sleep", "10"]   # Allow draining
   ```
3. **Health checks** — both liveness and readiness probes must work.
4. **Resource availability** — ensure cluster has capacity for `maxSurge` pods.

**Execution & Monitoring:**
```bash
kubectl set image deployment/<app> <container>=<new-image>
kubectl rollout status deployment/<app>
kubectl rollout history deployment/<app>
kubectl rollout undo deployment/<app>   # if needed
```

**Service-level:**
- Use `sessionAffinity: None` for load distribution
- Ensure load balancer/ingress has healthy backend check

### 19) When would you use blue-green versus canary deployment?

| Aspect | Blue-Green | Canary |
|--------|-----------|--------|
| **How it works** | Two identical environments; switch traffic from blue to green all at once | Gradually shift traffic percentage to new version |
| **Risk** | Low — instant rollback by switching back | Low — limited blast radius |
| **Resource cost** | High — need double infrastructure | Low — only a small % of new version |
| **Real user validation** | Limited — goes live all at once | Excellent — progressive exposure |
| **Rollback speed** | Instant | Gradual — stop promotion |
| **Best for** | Major version upgrades, database migrations, zero-risk deployments | Incremental releases, feature flags, A/B testing |
| **Complexity** | Simpler — just switch a load balancer | More complex — need traffic splitting (Istio, Argo Rollouts, Flagger) |

**Blue-Green Use Cases:**
- Full environment swap with zero risk
- When you need to test in production-identical environment before cutover
- Quick rollback is critical

**Canary Use Cases:**
- When you need gradual validation with real users

### 20) How would you manage Helm releases across environments?

### 21) How would you troubleshoot node pressure and evictions?

**Identify Pressure:**

1. **Check node conditions** — `kubectl get nodes` and look for conditions:
   - `MemoryPressure=True`
   - `DiskPressure=True`
   - `PIDPressure=True`
2. **Describe the node** — `kubectl describe node <node>` for detailed conditions and events.
3. **Check events** — `kubectl get events --field-selector reason=Evicted`

**Troubleshoot by Type:**

| Pressure Type | Commands | Fix |
|--------------|----------|-----|
| **Memory** | `free -h`, `dmesg \| grep oom`, `kubectl top node` | Scale down workloads, increase node memory, set memory limits |
| **Disk** | `df -h`, `docker system df` (or `crictl rprune`) | Clean up images, increase disk, configure `evictionHard` |
| **PID** | `cat /proc/sys/kernel/pids_max`, `ls /proc \| wc -l` | Reduce containers per node, fix fork bombs |
| **ImageFS** | `df -h /var/lib/kubelet` | Prune unused images: `crictl rprune` |

**Kubelet Eviction Config:**
```yaml
# kubelet configuration
evictionHard:
  memory.available: "100Mi"
  nodefs.available: "10%"
  imagefs.available: "15%"
evictionSoft:
  memory.available: "500Mi"
evictionSoftGracePeriod:
  memory.available: "1m30s"
```

**Prevention:**
- Set resource requests/limits on all pods
- Use `LimitRange` and `ResourceQuota` in namespaces
- Monitor with Prometheus + Node Exporter
- Use `Vertical Pod Autoscaler` to right-size requests
- Enable cluster autoscaler for horizontal scaling

### 22) How would you design HA Kubernetes workloads across zones?

**Cluster-level HA:**

1. **Multi-zone control plane** — deploy API servers and etcd across 3+ availability zones
2. **etcd quorum** — odd number of etcd members (3 or 5) across zones

**Workload-level HA:**

1. **Replica sets** — run at least 3 replicas for critical workloads
2. **Pod Anti-Affinity** — spread pods across nodes/zones:
   ```yaml
   affinity:
     podAntiAffinity:
       preferredDuringSchedulingIgnoredDuringExecution:
       - weight: 100
         podAffinityTerm:
           labelSelector:
             matchExpressions:
             - key: app
               operator: In
               values: [myapp]
           topologyKey: topology.kubernetes.io/zone
   ```
3. **Topology Spread Constraints** — even distribution:
   ```yaml
   topologySpreadConstraints:
   - maxSkew: 1
     topologyKey: topology.kubernetes.io/zone
     whenUnsatisfiable: DoNotSchedule
   ```
4. **Pod Disruption Budgets** — ensure minimum availability during maintenance:
   ```yaml
   apiVersion: policy/v1
   kind: PodDisruptionBudget
   metadata:
     name: myapp-pdb
   spec:
     minAvailable: 2
     selector:
       matchLabels:
         app: myapp
   ```
5. **Multi-zone Load Balancer** — use cloud NLB/ALB with health checks across zones
6. **Local SSD + zone-local caching** — for stateful workloads, replicate data across zones
7. **Node selectors / zone-aware scheduling** — for latency-sensitive workloads

**Disaster Recovery:**
- Velero for cluster backup/restore
- Cross-region replication for etcd and object storage
- Pre-warmed standby cluster in secondary region

### 24) How would you design GitHub Actions workflows for multiple environments?

**Workflow structure:**

```yaml
# .github/workflows/deploy.yml
name: Deploy to Environments

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # 1. Build and test (runs on every PR and push)
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: npm test
      - name: Build image
        run: docker build -t ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} .
      - name: Push image
        if: github.ref == 'refs/heads/main'
        run: |
          echo ${{ secrets.GITHUB_TOKEN }} | docker login ${{ env.REGISTRY }} -u ${{ github.actor }} --password-stdin
          docker push ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}

  # 2. Deploy to staging (auto on main push)
  deploy-staging:
    needs: build
    if: github.ref == 'refs/heads/main'
    uses: ./.github/workflows/deploy-env.yml
    with:
      environment: staging
      image-tag: ${{ github.sha }}
    secrets: inherit

  # 3. Deploy to production (manual approval)
  deploy-production:
    needs: deploy-staging
    if: github.ref == 'refs/heads/main'
    uses: ./.github/workflows/deploy-env.yml
    with:
      environment: production
      image-tag: ${{ github.sha }}
    secrets: inherit

# .github/workflows/deploy-env.yml (reusable)
on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
      image-tag:
        required: true
        type: string
jobs:
  deploy:
    environment: ${{ inputs.environment }}  # Triggers approval gates
    runs-on: ubuntu-latest
    steps:
      - name: Deploy
        run: |
          helm upgrade --install myapp ./charts/myapp \
            --set image.tag=${{ inputs.image-tag }} \
            -f charts/myapp/values-${{ inputs.environment }}.yaml \
            -n ${{ inputs.environment }}
```

**Key Design Principles:**
- **Reusable workflows** — `workflow_call` for DRY environment deployments
- **Environment protection rules** — manual approval for production, branch restrictions
- **Matrix strategy** — for multi-language or multi-arch builds
- **Concurrency controls** — `concurrency: { group: deploy-${{ github.ref }}, cancel-in-progress: true }`
- **Secrets per environment** — use GitHub Environments for scoped secrets
- **Caching** — `actions/cache` for npm/maven/pip dependencies

deploy_production:

    - if: $CI_PIPELINE_SOURCE == "pipeline"  # Triggered from another pipeline

3. **Helm rollback** — `helm rollback <release> <revision>` tracked in CI
4. **GitLab Environment tracking** — each deployment creates a revision, rollback restores previous
5. **Retry with backoff** — use `retry: 2` in job config for transient failures
6. **Downstream pipeline for rollback** — trigger a rollback pipeline from a scheduled job if monitors detect issues

### 30) How would you design HA load balancing across availability zones?

**Architecture:**

```
                    ┌─────────────────┐
                    │   Cloud LB      │
                    │ (NLB/ALB/LB)    │
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │ AZ-1       │  │ AZ-2       │  │ AZ-3       │
     │ App Nodes  │  │ App Nodes  │  │ App Nodes  │
     └────────────┘  └────────────┘  └────────────┘
```

**Design elements:**

1. **Layer 7 Load Balancer (ALB/HTTP LB)** — for HTTP/HTTPS, path-based routing, WAF integration
2. **Layer 4 Load Balancer (NLB/TCPLB)** — for TCP/UDP, lowest latency, static IP
3. **Cross-zone load balancing** — enabled by default on ALB; ensures even distribution across zones
4. **Health checks** — configure path, interval, threshold:
   - Healthy threshold: 3, Unhealthy: 3, Interval: 10s
   - Targets deregistered automatically if unhealthy
5. **Target groups** — one per AZ or shared, with proper port/protocol config
6. **DNS failover** — Route 53 / Cloud DNS with failover routing policies
7. **Multi-region** — Global Traffic Manager / Cloud Endpoints / DNS failover for cross-region

**Best Practices:**
- Register targets from all 3 AZs
- Use connection draining (deregistration delay) for graceful removal
- Enable access logs for debugging
- Use WAF for Layer 7 LB for DDoS/injection protection
- Set idle timeout appropriately (AWS ALB default: 60s)
- Use sticky sessions only if application requires

### 31) How would you configure auto scaling for unpredictable traffic?

**Multi-dimensional scaling strategy:**

1. **Target Tracking (most common)** — scale to keep a metric at a target value:
   ```
   Metric: CPU Utilization → Target: 60%
   Metric: Request Count per Target → Target: 1000
   ```

2. **Step Scaling** — different scale-out/in adjustments based on metric magnitude:
   ```
   CPU 70-80%  → Add 2 instances
   CPU 80-90%  → Add 5 instances
   CPU 90%+    → Add 10 instances
   ```

3. **Scheduled Scaling** — predict traffic patterns (e.g., business hours, known events):
   ```
   08:00 → Scale to 10 instances
   20:00 → Scale to 3 instances
   ```

4. **Predictive Scaling** — AWS Predictive Scaling / GCP MIGs use ML to pre-scale based on historical patterns.

**Configuration example (AWS ASG + K8s HPA):**

```yaml
# Kubernetes HPA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 3
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
  - type: Pods
    pods:
      metric:
        name: requests-per-second
      target:
        type: AverageValue
        averageValue: "1000"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Pods
        value: 4
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 2
        periodSeconds: 120
```

**Key considerations:**
- **Scale-up vs scale-down asymmetry** — scale up fast, scale down slowly (stabilization window)
- **Custom metrics** — use Prometheus Adapter for queue depth, business KPIs
- **Cluster Autoscaler** — auto-provision nodes when pods can't be scheduled
- **Karpenter** — faster, more efficient node provisioning for K8s
- **Warm pool** — pre-warm instances for faster scale-up
- **Cooldown periods** — prevent oscillation (rapid scale-up/scale-down cycles)

### 33) How would you design disaster recovery with defined RPO/RTO?

**RPO (Recovery Point Objective)** — max data loss tolerated
**RTO (Recovery Time Objective)** — max downtime tolerated

**DR Strategies by tier:**

| Strategy | RTO | RPO | Cost | Use Case |
|----------|-----|-----|------|----------|
| **Backup & Restore** | Hours | Hours | $ | Non-critical, compliance |
| **Pilot Light** | Minutes-Hours | Minutes | $$ | Core services always warm |
| **Warm Standby** | Minutes | Near-zero | $$$ | Production workloads |
| **Multi-Active** | Seconds | Zero | $$$$ | Mission-critical |

**Design for K8s + Cloud:**

1. **Backup strategy:**
   - **Velero** — cluster resources + persistent volumes backup
   - **etcd snapshots** — `ETCDCTL_API=3 etcdctl snapshot save`
   - **Database** — cross-region replication (RDS Multi-AZ, read replicas)
   - **Object storage** — cross-region replication (S3 CRR, GCS DRS)

2. **Infrastructure as Code** — Terraform/CDK to provision standby region from code
3. **DNS failover** — Route 53 / Cloud DNS health check + failover routing
4. **Data replication:**
   - Databases: async replication to DR region
   - Object storage: cross-region replication
   - Message queues: cross-region mirroring (SQS, Pub/Sub)

5. **Runbook for failover:**
   ```
   1. Declare incident, notify stakeholders
   2. Update DNS to point to DR region
   3. Promote DR database to primary
   4. Scale up DR cluster
   5. Verify services healthy
   6. Communicate restoration
   ```

6. **Testing:**
   - Quarterly DR drills
   - Automated chaos engineering (Chaos Mesh, Gremlin)
   - Measure actual RTO/RPO against targets

**Example RPO/RTO targets:**
- **Tier 1 (Critical):** RTO < 15 min, RPO < 5 min → Multi-Active + sync replication
- **Tier 2 (Important):** RTO < 1 hour, RPO < 15 min → Warm Standby + async replication
- **Tier 3 (Standard):** RTO < 4 hours, RPO < 1 hour → Pilot Light + backups

### 34) How would you investigate sudden cloud cost increases?

**Systematic approach:**

1. **Identify the spike:**
   - Check cost management dashboards (AWS Cost Explorer, Azure Cost Management, GCP Billing)
   - Filter by service, region, account, tag
   - Compare day-over-day and month-over-month

2. **Common causes:**

| Service | Cause | Investigation |
|---------|-------|---------------|
| **EC2/VMs** | Forgotten dev/test instances, larger instance types | `aws ec2 describe-instances`, tag analysis |
| **Data Transfer** | Cross-AZ/region traffic, egress to internet | VPC Flow Logs, CloudWatch metrics |
| **RDS/Database** | Upgraded instance, provisioned IOPS, backups | RDS console, storage metrics |
| **S3/Storage** | New storage class, large data ingestion | S3 storage analysis, bucket metrics |
| **Load Balancer** | New ALB/NLB, processing more requests | LB metrics, request count |
| **Lambda/Functions** | Increased invocations, longer duration, more memory | Lambda metrics, CloudWatch Logs |
| **EKS/K8s** | More nodes, spot instance interruptions | Node count, `kubectl get nodes` |
| **API calls** | Excessive API calls from misconfigured app | CloudTrail analysis |
| **NAT Gateway** | High data processing through NAT | NAT Gateway metrics |

3. **Tag-based analysis** — group costs by `Environment`, `Team`, `Project` tags
4. **Set up alerts** — AWS Budgets / Azure Budgets / GCP Budget alerts at 80%, 100%, 120%
5. **Right-sizing** — identify underutilized resources:
   - AWS Compute Optimizer / Azure Advisor / GCP Recommender
   - Reserved Instances / Savings Plans coverage
6. **Anomaly detection** — enable AWS Anomaly Detection / GCP Anomaly-based insights

**Prevention:**
- Enforce tagging policies
- Set spending limits per team/project
- Use SCPs / Azure Policy to restrict instance types/regions
- Schedule auto-shutdown for non-prod
- Implement showback/chargeback

### 35) How would you resolve Terraform state locking issues?

**Understanding state locking:**
Terraform locks state to prevent concurrent operations from corrupting it. Locks are held by the backend (S3 + DynamoDB, Consul, etc.).

**Diagnosis:**

1. **Check for running operations** — is another `terraform apply` / `plan` still running?
2. **Identify the lock:**
   ```bash
   # For S3 + DynamoDB backend
   aws dynamodb scan --table-name terraform-locks --query "Items[?LockID]"

   # Output shows LockID, Info (who/where), and Operation
   ```

3. **Common causes:**
   - `terraform apply` was interrupted (Ctrl+C, crash, timeout)
   - CI/CD pipeline failed without releasing the lock
   - Multiple users/CI jobs running simultaneously

**Resolution:**

1. **Wait** — if a legitimate operation is in progress, wait for it to complete.
2. **Force unlock** (only if you're certain no operation is running):
   ```bash
   terraform force-unlock <LOCK_ID>
   ```
3. **Delete lock manually** (last resort):
   ```bash
   # DynamoDB
   aws dynamodb delete-item --table-name terraform-locks --key '{"LockID": {"S": "<lock-key>"}}'
   ```

**Prevention:**
- Set `lock_timeout` in backend config
- Use CI/CD queueing to prevent concurrent runs
- Implement proper error handling in CI to release locks on failure
- Use `terraform plan` before `apply` to catch issues early

### 36) How would you safely manage remote state across teams?

**Backend Configuration:**

```hcl
# S3 + DynamoDB (AWS)
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "team-a/prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}
```

**State Organization Strategies:**

1. **One state per environment per team:**
   ```
   s3://terraform-state/
   ├── team-a/
   │   ├── dev/terraform.tfstate
   │   ├── staging/terraform.tfstate
   │   └── prod/terraform.tfstate
   └── team-b/
       ├── dev/terraform.tfstate
       └── prod/terraform.tfstate
   ```

2. **State isolation** — each team/environment has its own state file to:
   - Prevent cross-team dependencies
   - Allow independent deployments
   - Limit blast radius of state corruption

3. **Shared state via `terraform_remote_state` data source:**
   ```hcl
   # Team B needs VPC ID from Team A's state
   data "terraform_remote_state" "networking" {
     backend = "s3"
     config = {
       bucket = "my-terraform-state"
       key    = "networking/prod/terraform.tfstate"
       region = "us-east-1"
     }
   }

   vpc_id = data.terraform_remote_state.networking.outputs.vpc_id
   ```

4. **Access control:**
   - **S3 bucket policy** — restrict by IAM role/user
   - **DynamoDB IAM policy** — lock/unlock permissions
   - **State encryption** — SSE-S3 or SSE-KMS with key policies

5. **State management best practices:**
   - Never edit state manually (use `terraform state mv` / `rm`)
   - Versioning enabled on S3 bucket for state history
   - Regular state backups
   - Use `terraform plan` to review changes before applying
   - Store state in a dedicated account (not the same as workload)

6. **Workspace management** — `terraform workspace` for env separation (use cautiously, prefer separate state files).

### 37) How would you handle Terraform drift in production?

**Detecting Drift:**

1. **Regular `terraform plan`** — schedule in CI to run daily and detect unmanaged changes:
   ```yaml
   # GitHub Actions - Daily drift detection
   on:
     schedule:
       - cron: '0 6 * * *'  # Daily at 6 AM
   jobs:
     drift-detect:
       runs-on: ubuntu-latest
       steps:
         - uses: hashicorp/setup-terraform@v3
         - run: terraform init
         - run: terraform plan -detailed-exitcode
           continue-on-error: true
   ```

2. **Drift detection tools** — **driftdetect** (commercial), **spacelift**, **env0**

**Responding to Drift:**

| Scenario | Action |
|----------|--------|
| **Intentional manual change** | Import into Terraform: `terraform import` or write code to match |
| **Unintentional change** | `terraform apply` to revert to desired state |
| **Resource removed outside Terraform** | `terraform plan` shows destroy; verify and apply, or refresh state |
| **Configuration drift** | Update Terraform code to match desired state, then apply |

**Handling specific drift:**

```bash
# 1. Resource modified outside Terraform
terraform plan          # Shows the diff
terraform apply         # Reverts to Terraform-managed state

# 2. Resource created outside Terraform, needs to be imported
terraform import aws_instance.web i-1234567890abcdef0

# 3. Resource no longer exists in cloud
terraform state rm aws_instance.old
terraform apply

# 4. Refresh state without applying
terraform refresh       # Updates state to match real infrastructure
```

**Prevention:**
- **Restrict manual access** — SCPs / Azure Policy to prevent console modifications
- **Use only IaC for changes** — enforce through change management process
- **CloudTrail / Activity Log monitoring** — alert on console/API changes to Terraform-managed resources
- **Sentinel / OPA policies** — enforce that all changes go through Terraform
- **SSM Automation / Change Manager** — for approved manual changes, track and reconcile

**Module Design (VPC example):**

```hcl
# modules/vpc/main.tf
resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = merge(var.common_tags, {
    Name = "${var.environment}-vpc"
  })
}

resource "aws_subnet" "public" {
  count             = length(var.availability_zones)
  vpc_id            = aws_vpc.this.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index)
  availability_zone = var.availability_zones[count.index]

  tags = {
    Name = "${var.environment}-public-${var.availability_zones[count.index]}"
  }
}

# modules/vpc/outputs.tf
output "vpc_id" {
  value       = aws_vpc.this.id
  description = "The ID of the VPC"
}

output "public_subnet_ids" {
  value       = aws_subnet.public[*].id
  description = "List of public subnet IDs"
}
```

**Environment root module:**

```hcl
# environments/prod/main.tf
module "vpc" {
  source = "../../modules/vpc"

  environment        = "prod"
  vpc_cidr           = var.vpc_cidr
  availability_zones = var.availability_zones
  common_tags        = var.common_tags
}

module "eks" {
  source = "../../modules/eks"

  cluster_name    = "${var.environment}-eks"
  vpc_id          = module.vpc.vpc_id
  subnet_ids      = module.vpc.public_subnet_ids
  common_tags     = var.common_tags
}
```

**Best Practices:**
- **Module versioning** — publish to Terraform Registry or use Git refs: `source = "git::https://github.com/org/modules//vpc?ref=v1.2.0"`
- **Inputs/outputs** — keep interfaces clean and well-documented
- **No hardcoded values** — all configuration via variables with sensible defaults
- **`terraform.tfvars` per environment** — override defaults for each environment
- **`pre-commit` + `tflint` + `terrascan`** — lint and security scan in CI
- **`terraform validate` and `terraform plan` in CI** — before any merge
- **Dependency management** — avoid circular dependencies between modules

### 39) When would you use Terraform versus Ansible?

| Aspect | Terraform | Ansible |
|--------|-----------|---------|
| **Purpose** | Infrastructure provisioning (create/destroy resources) | Configuration management (configure running systems) |
| **Paradigm** | Declarative — define desired state | Procedural — define steps/tasks |
| **Idempotency** | Built-in (state file tracks resources) | Built-in (task-level) |
| **State** | Maintains state (local or remote) | Stateless |
| **Scope** | Cloud resources, IaC (VPCs, K8s clusters, DBs) | OS-level config, app deployment, package management |
| **Connectivity** | Cloud provider APIs (no agent) | SSH / WinRM (agentless but needs access) |
| **Strengths** | Multi-cloud, resource lifecycle, state management | In-host configuration, software installation, ad-hoc commands |

**When to use each:**

| Scenario | Tool |
|----------|------|
| Create VPC, subnets, security groups | **Terraform** |
| Provision EKS / AKS / GKE cluster | **Terraform** |
| Create RDS / Cloud SQL database | **Terraform** |
| Install Docker, Kubernetes tools on nodes | **Ansible** |
| Deploy application config files | **Ansible** |
| Manage users, SSH keys, firewall on VMs | **Ansible** |
| Update application packages on running servers | **Ansible** |
| Provision cloud load balancer | **Terraform** |
| Configure Nginx/Apache on servers | **Ansible** |

**Combined workflow:**
```
1. Terraform → Provision infrastructure (VPC, VMs, K8s cluster)
2. Terraform outputs → Pass connection details (IPs, credentials) to Ansible inventory
3. Ansible → Configure OS, install software, deploy applications
4. Ansible → Run post-deployment validation
```

```hcl
# Terraform: generate Ansible inventory
resource "local_file" "ansible_inventory" {
  content = templatefile("${path.module}/inventory.tpl", {
    hosts = aws_instance.app[*].public_ip
  })
  filename = "${path.module}/inventory.ini"
}
```

**Bottom line:** Terraform builds the house (infrastructure), Ansible furnishes it (configuration). Use both together for complete infrastructure automation.
